# Database

Postgres 17 on Supabase. All tables live in schema **`app`** (not exposed by Supabase's Data API;
RLS enabled on every table; `anon`/`authenticated` revoked — migration `0001_lock_down_app_schema`).
Schema source of truth: `src/server/db/schema/*.ts` (Drizzle, `casing: snake_case`).

## Old → new

The old MySQL database had one copy of every table per store (`drinks`, `drinks2` … `drinks6`, same
for `company`, `distribution`, `orders`, `momwodebeli`, `finance` …). Now one table per concept:

| New table | Old table(s) | Notes |
|---|---|---|
| `stores` | `names` + the suffix of each table set | per-store document counters live here |
| `users`, `user_stores`, `sessions` | `users` (+ hard-coded e-mails in `template.php`) | access is data now |
| `suppliers` | `momwodebeli{n}` | `is_returns` = old supplier 4 "დაბრუნებული" |
| `products` | `drinks{n}` | `stock_qty` = old `count` |
| `product_price_changes` | `drinks{n}_edited` | old rows have only the *old* prices |
| `customers` | `company{n}` | `color`, `comment` kept |
| `deliveries` | `distribution{n}` | = "ოპერაცია"; `number` = old id |
| `delivery_items` | `drinks{n}_count` | only non-zero rows (the old forms saved a row for every product) |
| `orders`, `order_items` | `orders{n}`, `drinks{n}_count_orders` | status 0/1/3 → open/completed/cancelled |
| `stock_receipts`, `stock_receipt_items` | `drinks{n}_history` (rows sharing an id) | |
| `stock_adjustments` | — | new: inventory corrections |
| `finance_accounts` | the `finance*` tables | default book per store; stores 1–2 also have "ფინანსები 2" (`finance2`, `finance4`) |
| `finance_entries` | `finance`, `finance3`, `finance5`, `finance7`, `finance9`, `finance11`, `finance2`, `finance4` | links to delivery / supplier / employee |
| `employees`, `wage_accruals` | `employees`, `wages_history` | wage payments are `finance_entries` (kind `wage_payment`) |
| `audit_log` | — | who changed what (also the login throttle: `auth.login_failed` rows) |
| `request_keys` | — | one row per create sent with a request id — stops double submits (`once()`) |
| — | `hours`, `time*` | dropped: unused PlayStation-timer experiment and dead tables |

Store mapping: set1 = names.id 1 (გეალკო თბილისი), set2 = 4 (გეალკო ბათუმი), set3 = 5 (ტექნოჰაბი),
set4 = 6 (ბროწეული ვაინს), set5 = 7 (Akriani Tbilisi), set6 = 8 (Brand Wine). Cash books:
set1 → `finance` (+`finance2`), set2 → `finance3` (+`finance4`), set3 → `finance5`, set4 → `finance7`,
set5 → `finance9`, set6 → `finance11`.

## Derived values (never stored)

| Value | Formula | Old column it reproduces |
|---|---|---|
| Customer debt after operation N | `SUM(total_amount − paid_amount + adjustment_amount) OVER (PARTITION BY customer_id ORDER BY id)` | `distribution.darchenili` |
| Customer current debt | same SUM over all the customer's operations | latest `darchenili` |
| Cash-book balance after entry N | `SUM(amount_in − amount_out + adjustment_amount) OVER (ORDER BY id)` per account | `finance.balance` |
| Supplier "remaining to pay" | Σ(receipt qty × unit_cost) − Σ(`amount_out` of entries with supplier_id) | `historylistmomw` |

`adjustment_amount` holds corrections: imported rows where the old stored value did not follow
the formula (manual phpMyAdmin edits) carry the exact difference, so **every historical number is
identical to the old app**, and editing or deleting anything automatically re-flows all later
balances. New debt corrections are `deliveries.kind = 'adjustment'` rows.

Stock is stored (`products.stock_qty`) and only changed in the transaction that moves goods
(operation create/edit/delete, order completion, receipt create/delete, inventory correction).

## Indexes

Every foreign key used for lookups is indexed; the hot paths are
`deliveries(customer_id, id)`, `deliveries(store_id, delivery_date)`, `delivery_items(delivery_id)`,
`finance_entries(account_id, id)`, `orders(store_id, status, id)`, `audit_log(action, created_at)`
(login throttle). Unique: `(store_id, number)` on deliveries, orders and receipts. Window functions
over a store's ~10k operations take a few ms.

## Migrations

```bash
# 1. edit src/server/db/schema/*.ts
npm run db:generate -- --name short_description   # writes drizzle/NNNN_*.sql — review it!
npm run db:migrate                                 # applies to DATABASE_URL_SESSION
```

Hand-written SQL: `npx drizzle-kit generate --custom --name x`. Never edit an applied migration.
The applied list lives in `drizzle.__drizzle_migrations`. New tables get the same `anon` /
`authenticated` revoke as `0001` (see `0003_request_keys_and_login_index.sql`).

## Conventions

- Ids: `integer generated by default as identity` (the import sets explicit ids, then resets sequences).
- Money `numeric(18,4)`, discount factor `numeric(6,4)`, quantities `integer` (may be negative = return).
- Business dates `date` (string `YYYY-MM-DD`, parser overridden in `server/db/pool.ts`);
  timestamps `timestamptz`.
- `legacy_*` columns / `legacy` jsonb: traceability to the old DB (old ids, raw non-numeric text).
